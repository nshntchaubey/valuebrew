# ValueBrew — Recommendation Engine Implementation

*Business-logic architecture, not UX, not a screen spec, not a widget spec. This document specifies the engine that turns a Catalog plus a person's stated constraints into a `RecommendationOutcome` — nothing about how that outcome is displayed. Grounded directly in the real, shipped `lib/features/recommendation/domain/` files (read in full: `generate_recommendation.dart`, `recommendation_outcome.dart`, `recommendation_result.dart`, `tied_candidate.dart`), the real, unreachable Generation-1-lineage engine (`services/recommendation_engine.dart`, `scoring/weighted_scorer.dart`, `scoring/similarity_strategy.dart`, `models/recommendation.dart`, `models/recommendation_reason.dart`, also all read in full), and Decision Engine 2.0's own thirteen-point Recommendation reasoning model, cross-referenced against Beer Knowledge Model 2.0, Domain Model 1.0, Beer Entity Specification 1.0, Product Definition, the Product Decisions Register, and the Recommendation Experience Specification.*

---

## 0. The One Conclusion That Governs Everything Below

**The real, shipped engine already correctly implements Decision Engine 2.0's reasoning model for today's two-input case (budget, style), and needs no behavioral change for catalog integration.** `generateRecommendation()` is a pure function over an arbitrary `Catalog` — it makes no assumption anywhere about catalog size, specific SKU identities, or how many beers exist. Loading a real, several-hundred-SKU catalog in place of today's one-SKU placeholder changes *what data flows through it*, not *what it does*. This document specifies that same engine, precisely, names exactly where it already meets Decision Engine 2.0's model and where a real gap remains, and is explicit, per instruction, everywhere a gap traces back to an unresolved Product Decision rather than an implementation choice this document is free to make.

---

## Part 1 — Responsibilities

**What the engine owns.** Given a Catalog and a stated Hard Constraint (budget) plus an optional Strong Preference (style), it owns: filtering candidates against every stated Hard Constraint; determining whether one candidate dominates on the stated Strong Preference; detecting a genuine tie when multiple candidates are equally best; generating the Explanation for whichever outcome results, in the same pass that determines the outcome, never afterward; and returning exactly one of the four defined `RecommendationOutcome` variants. This is the entire Decision Engine Model's Recommendation reasoning surface, and nothing more.

**What it explicitly does not own**, stated precisely because each of these has a real, identifiable owner elsewhere:
- **Gathering input.** The engine never asks a question, reads a text field, or decides what to ask next — that's `RecommendationScreen`'s own local state and its `_regenerate` call path (confirmed directly in the Recommendation Widget Specification). The engine receives already-disambiguated `double budget`/`String? styleId` values; whether a person's raw input was ambiguous (Product Decisions Register D6) is resolved, if at all, before it ever reaches this function.
- **Planning Mode.** Confirmed directly: `generateRecommendation` takes no Planning Mode parameter anywhere in its real signature. Planning Mode is a display-only flag threaded through `RecommendationScreen`'s own `isPlanning` field, shown as `_PlanningModeBanner`, and never touches reasoning. The engine's output is identical whether or not Planning Mode is active — this is a correct, already-existing boundary, and this document does not propose changing it.
- **Session state, of any kind.** The engine holds no memory between calls. Every call is independent, given whatever budget/style the caller currently has. `RecommendationScreen`'s own `_budgetController`/`_selectedStyleId` fields are the session state, held entirely outside this engine.
- **Presentation, entirely.** Typography, spacing, copy beyond the Explanation string's own content, navigation — none of this is the engine's concern, and none of it is addressed here.
- **Catalog construction.** The engine trusts whatever `Catalog` it's given; it does not validate, build, or enrich it. That's the Catalog Builder's job, entirely, per Catalog Contract 1.0 and Catalog Builder Implementation Design — both frozen, neither revisited here.
- **Multi-candidate relational reasoning (Comparison), verification (Price Verification), or single-beer explanation without ranking (Beer Detail).** Each belongs to a different reasoning surface per Decision Engine 2.0's own Ownership Matrix (Part 8) — the engine never reaches into any of them.

## Part 2 — Inputs

**Catalog.** The full, already-validated `Catalog` object — `styles`, `beers`, `skus`, `benchmarks` — exactly as Catalog Contract 1.0 defines it. The engine reads `catalog.skus` directly and resolves references (`resolveBeer`, `resolveStyle`) via the same shared `catalog_lookups.dart` functions every other screen already uses — no separate lookup logic of its own.

**Constraints.** Today, exactly one: `budget` (`double`, required) — the sole Hard Constraint, per Decision Engine 2.0 Part 2, point 3 ("Nothing proceeds — no candidate set exists to reason over — without it"). No other Hard Constraint exists in the real signature today.

**Preferences.** Today, exactly one, optional: `styleId` (`String?`) — the sole Strong Preference, per Decision Engine 2.0 Part 2, point 4. Canon separately names strength, size, and brand as inputs the Decision Engine Model orders after budget and style (same point) — **none of these are gathered by the current build, and this document does not add them.** The real engine's own doc comment already names this precisely as a deliberate, not-yet-built extension seam ("further Progressive Question-Asking (strength, size, brand) once budget and style alone leave candidates too close together") — restated here as still accurate, not as a new finding.

**Planning mode.** Not an engine input, per Part 1. Stated here again only to be unambiguous: this section has nothing to add for it, because it never reaches the engine.

**Session state.** Not an engine input, per Part 1, for the same reason.

## Part 3 — Evaluation Pipeline

Mapped directly onto the real code's own actual steps, in order — no step below is invented; each is either already implemented exactly as described or explicitly marked as not yet built.

1. **Filtering — Hard Constraints.** `catalog.skus.where((sku) => sku.price <= budget)`. Every SKU violating the stated budget is excluded, unconditionally, before anything else happens — Decision Engine 2.0 Part 2, point 9's own rule ("filter strictly by every stated Hard Constraint first"), implemented exactly.
2. **Empty check — Conflicting/no-answer state.** If nothing survives step 1, the pipeline stops immediately and returns `NoRecommendationWithinBudget` — the real code's own honest, correctly-scoped outcome for "no real candidate satisfies the stated Hard Constraint at all" (Decision Engine 2.0 Part 2, point 7).
3. **Filtering — Soft/Strong Preferences.** If `styleId` is given, narrow the Hard-Constraint survivors to those whose resolved Beer shares that style. If `styleId` is `null`, this step is a no-op — the same candidate set from step 1 carries forward unchanged, which is exactly what makes the styleId-omitted case "mechanically identical to this vertical slice's original budget-only behaviour," per the real code's own doc comment.
4. **Empty check — style-specific no-match state.** If step 3 leaves nothing, return `NoRecommendationMatchingStyle` — real candidates exist within budget, just none matching the stated style; a distinct, correctly-separated outcome from step 2's, per Decision Engine 2.0 Part 2's own point 7 framing (this is not a Hard Constraint failure, it's a Strong Preference yielding zero survivors, and the real code already keeps these two failure modes distinct rather than collapsing them).
5. **Tie detection.** A single linear scan tracking the current best `valueScore` and every SKU currently tied with it — `valueScore` is `int`-typed on the real `Sku` model (confirmed directly), so this comparison is **exact integer equality, never a floating-point epsilon question** — worth stating plainly since it removes an entire category of tie-detection correctness concern before it can arise.
6. **Trade-off generation — not built, and correctly so.** The real code's own doc comment names exactly why: a Trade-off Explanation "requires two conflicting Strong Preferences to exist simultaneously — not reachable with today's single optional style preference." With only one Strong Preference in play, a Trade-off is structurally impossible to produce today; this is not a gap, it's the correct absence of a capability whose precondition doesn't yet exist.
7. **Confidence generation — not a separate step, and this is worth stating explicitly since the request asks for it as one.** There is no discrete confidence computation anywhere in the real code, and none is proposed here. Per Beer Detail Screen Contract's own already-established precedent (directly applicable, since Recommendation draws from the identical Beer Knowledge Base): every fact this engine reasons over — price, ABV, Value Score — is uniformly Verified or Computed. There is no Soft-Preference-driven content anywhere in today's two-input model (style is Strong, not Soft), so there is no mixed-confidence case for a dedicated step to resolve. Confidence is expressed entirely through the Explanation's own language register (certainty-then-judgment, per the Conversation Model), not through a separate artifact.
8. **Explanation generation — happens in the same pass as steps 5–6, never afterward.** The real code builds its explanation string using the exact same `budget`, `styleClause`, and `tied`/`best` values the outcome itself was just determined from — there is no separate "now explain what happened" pass reading the result back. This is Decision Engine 2.0 Part 2, point 10's own recovered mechanical guarantee, already correctly implemented, restated in Part 6 below.
9. **`RecommendationOutcome` creation.** Wraps the single winner in `RecommendationFound(RecommendationResult(...))`, or the tied set in `RecommendationTie(candidates, explanation)` — the final, single return point of the whole function.

## Part 4 — RecommendationResult

*Covering the full real output type family, since "RecommendationResult" in the broader sense the request means spans three real classes.*

**`RecommendationOutcome`** (sealed, `recommendation_outcome.dart`) — the actual top-level return type of `generateRecommendation`. Four concrete subclasses, exhaustively:
- `RecommendationFound(RecommendationResult result)` — a single winner.
- `NoRecommendationWithinBudget()` — no fields, a plain marker.
- `NoRecommendationMatchingStyle()` — no fields, a plain marker.
- `RecommendationTie(List<TiedCandidate> candidates, String explanation)` — multiple winners.

Every field on every variant is `final`; every variant's constructor is `const` where the shape allows it. **Lifecycle:** created once, at the moment `generateRecommendation` returns, held in `RecommendationScreen`'s local `_outcome` state, replaced wholesale (never mutated) on every re-run. **Ownership:** the domain layer owns the type definition; the presentation layer owns holding an instance of it. **Immutability:** total — no setter, no mutating method, anywhere in any of the four variants; a new outcome is always a new object, never an edit of the old one. The one computed, non-stored property — `canBeRefinedFurther` — is a `switch` over the sealed type, exhaustive by construction (the compiler forces a new case the moment a fifth variant is ever added), implementing the precise invariant Decision Engine 2.0's own model implies: refinement remains meaningful exactly when at least one SKU still satisfies every stated Hard Constraint, independent of whether the current Strong Preference is currently satisfied.

**`RecommendationResult`** (`recommendation_result.dart`) — the single-winner payload: `sku` (`Sku`), `beer` (`Beer`), `explanation` (`String`). Three fields, all required, all final. Explicitly documented as representing "the single-result case only" — a genuine tie is a structurally different type (`RecommendationTie`), never this class with a list bolted on. **No `fromJson`/`toJson` exists, deliberately** — this is always computed at runtime, never persisted or read from the catalog, consistent with the Product Definition's own no-accounts, no-persisted-history boundary.

**`TiedCandidate`** (`tied_candidate.dart`) — `sku` and `beer` only, **no explanation field of its own.** The tie's explanation lives once, on the parent `RecommendationTie`, shared across every member — correct, since the explanation ("these are equivalent on everything you've told me matters") describes the relationship between the candidates, not any one of them individually; duplicating it per-candidate would be redundant, not more informative.

## Part 5 — Decision Rules

**Hard constraints — budget, the only one today.** A SKU's `price` must be `<= budget`, strictly. No tolerance, no rounding, no "close enough" — Decision Engine 2.0's own explicit forbidden-assumptions list (Part 2, point 5) rules out any inference here; the comparison is exactly what's stated, nothing softened.

**Soft preferences — none exist in the current model, and this heading is answered by its own absence.** Style is a Strong Preference, not Soft, per Decision Engine 2.0's own three-tier taxonomy (Hard/Strong/Soft) — there is no Soft-Preference-driven filtering or ranking anywhere in this engine today. Restated because the request names this as its own decision-rule category; the correct answer is that the category is currently empty by design, not unimplemented.

**Budget.** Covered above — the sole Hard Constraint.

**Style.** The sole Strong Preference. When stated, it narrows (never broadens) the Hard-Constraint survivor set (Part 3, step 3). When a style-narrowed set dominates cleanly on Value Score, that's the answer; Decision Engine 2.0 Part 2 point 9's "if one dominates on every known Strong Preference, it wins outright" is trivially satisfied here since style is a filter, not a ranking dimension in its own right — Value Score alone breaks any remaining tie among style-matching candidates.

**Planning.** Not a decision rule at all — per Part 1/2, Planning Mode never reaches the engine and influences no rule here.

**Availability.** **Already fully handled, upstream, before the engine ever runs — not a rule this engine implements itself.** Every SKU in `catalog.skus` is, by Catalog Contract 1.0's own construction, already a currently-`LIVE` SKU; the Catalog Builder never publishes a `DELISTED` one into `catalog.json` at all. The engine has no `status`/`availability` field to check because there is structurally nothing to check — availability filtering already happened at the catalog-build layer, per Catalog Builder Architecture's own Publication Rules.

**Unknown data — the one heading that requires a real, evidence-grounded flag rather than a simple answer.** Decision Engine 2.0 Part 2's own point 6 names a real gap: "no canonical rule addresses what happens when a candidate SKU has an incomplete fact the ranking needs." **This document does not resolve that gap — Product Decisions Register D1 remains open, and this is exactly the kind of unresolved decision the instructions require flagging rather than silently deciding.** But a precise, evidence-based clarification belongs here, discovered by cross-referencing Catalog Contract 1.0 directly: **`Sku.abv` and `Beer.styleId` are both non-nullable fields in the real, frozen schema, and Catalog Contract 1.0 §7 already established that there is no schema mechanism today for publishing a Sku with an unknown ABV, or a Beer with an unresolved Style, at all.** A SKU missing ABV, or a Beer missing a confident Style assignment, is excluded from `catalog.json` entirely at the Catalog Builder's own publication gate (Catalog Builder Architecture's own mandatory-field rule) — it never reaches this engine as a runtime value to handle. **The practical consequence: this engine, as specified, never actually encounters an incomplete-ABV or unknown-style SKU, because the frozen schema already prevents one from existing in its input.** D1 is real and still open, but it is a **Catalog Builder publication decision** (should such a SKU ever be allowed to exist in `catalog.json` at all, e.g. via a future nullable-field schema change), not a **Recommendation Engine ranking decision** — resolving D1 toward "include with a caveat" would require amending Catalog Contract 1.0 first, and only then would this engine need new logic it does not need today. This document flags that dependency explicitly rather than building speculative handling for a data shape the current frozen contract cannot produce.

## Part 6 — Explanation Generation

**Exactly how explanations are built, today, precisely:** as a single string, interpolated directly from the same local variables — `budget`, `styleClause` (itself derived from the resolved `Style.name` when `styleId` is given), and either `best`/`beer` (single-winner case) or `tied`/`tied.first.valueScore` (tie case) — that were just used to determine the outcome itself. There is no separate "explain" function called after the fact with the outcome as its input; the explanation is built inline, in the same code path, from the same values, in the same pass Part 3 step 8 already describes.

**Reuse.** The style clause (`' and matching your preferred ${style.name} style'`) is computed exactly once and reused in both the single-winner and tie explanation templates — not duplicated logic, one shared fragment.

**Determinism.** Given the same `Catalog`, `budget`, and `styleId`, the function returns bit-for-bit the same `RecommendationOutcome` every time — no randomness, no wall-clock dependency, no external I/O anywhere in the function. This is a hard requirement the real code already satisfies and this document does not relax.

**No hallucinated reasoning — the discipline stated precisely, not just claimed.** Every fact appearing in an explanation string (`beer.name`, `best.sizeMl`, `best.valueScore`, `budget`, the style name) is read directly from already-validated `Catalog` data or the caller's own stated input — nothing is invented, estimated, or paraphrased by any generative process. This is mechanically guaranteed by construction, not merely a style guideline: there is no code path in `generateRecommendation` capable of producing a fact that isn't already sitting in one of its own inputs.

**The recovered discipline, worth naming explicitly since it's directly relevant even though it's not yet load-bearing today.** Decision Engine 2.0 Part 2, point 10 identifies this exact property — score and explanation computed together, from the same comparison, so an explanation can never disagree with what it's justifying — as recovered from Generation 1's own `SimilarityStrategy.score()`/`.explain()` pattern (confirmed directly in this session's own reading of `similarity_strategy.dart`: every strategy's `explain` method reuses a private helper its own `score` method also calls). **Today's single-dimension engine (Value Score alone) doesn't need that pattern's full generality — there's only one score to explain.** The moment a second ranking dimension is ever added (strength, size, brand — the real code's own already-named extension seam), that Gen1 pattern becomes the correct, already-proven implementation shape to reach for, precisely because it's the mechanism that makes Decision Engine 2.0's own explanation guarantee actually true at scale, not just at one dimension. This is a recommendation for *future* structure, not a change proposed to today's engine.

## Part 7 — Tie Logic

**Two-way.** The real algorithm (Part 3, step 5) handles this identically to any other count — there is no special-cased "exactly two" branch anywhere. Two candidates sharing the maximum `valueScore` simply both end up in the `tied` list.

**Three-way (and beyond).** **Already fully, correctly handled by the real algorithm, with no change needed** — this is worth stating plainly since Comparison's own equivalent tie-breaking logic (Product Decisions Register D5) has a real, unresolved 3+-candidate gap, and it would be easy to assume Recommendation shares it. It does not. Recommendation's tie detection is a linear scan over a flat list, comparing every candidate to the single running best `valueScore` — this generalizes to any number of tied candidates with no additional logic, since there is no pairwise or relational comparison happening at all, only "does this candidate's score equal the current maximum." **The reason Comparison's 3+ gap doesn't apply here:** Comparison's tie-breaker reasons about *relationships between named candidates on multiple dimensions*; Recommendation's tie detection reasons about *one dimension (Value Score) against a running maximum* — a structurally simpler problem that was never actually two-candidate-shaped to begin with, even before this document existed.

**Future compatibility.** If a second ranking dimension is ever added (Part 6's own noted extension seam), tie-breaking would need to become genuinely relational — "tied on Value Score, differentiated by dimension two" — at which point the current single-scan algorithm would need real revision, and the Gen1 `WeightedScorer` pattern (a combined weighted score across multiple dimensions, still reducible to one number to compare) is the natural shape that revision would take without reopening Comparison's own unresolved multi-candidate relational question. **This is noted as a future direction, not a change made or required by catalog integration itself** — today's real catalog, however large, still only ever produces a single-dimension Value Score per SKU, so today's tie logic remains fully correct and complete as specified.

## Part 8 — Low-Confidence Behaviour

**Recovery states — today, exactly two exist, and no more, on purpose.** `NoRecommendationWithinBudget` and `NoRecommendationMatchingStyle` are the engine's only two non-success outcomes. **A distinct Low-Confidence Response state, as Decision Engine 2.0 Part 2 point 13 describes it ("too little is known to meaningfully distinguish among a large field"), does not exist in the real code, and this document does not add one.** This matches the V1 Architecture Reference's own already-stated conclusion that this state is structurally unreachable given today's two-input surface — confirmed again here, independently, by this document's own inspection: with only budget and style as inputs, every possible input combination against any catalog, of any size, deterministically resolves to exactly one of the four defined `RecommendationOutcome` variants. There is no code path where "too little is known" could ever be true in a way distinct from "no candidates survive" (already `NoRecommendationWithinBudget`/`NoRecommendationMatchingStyle`) or "candidates remain genuinely equivalent" (already `RecommendationTie`). A real Low-Confidence state only becomes reachable once a third, genuinely optional input exists whose *absence* — not its value — could leave a field too undifferentiated to honestly rank; that input doesn't exist today.

**Incomplete catalog.** Per Part 5's own "Unknown data" finding: the engine never receives an incomplete SKU or Beer at all, by the frozen schema's own construction. "Incomplete catalog," at the engine's level, can only ever mean *small* — few real SKUs surviving a given budget/style combination — never *malformed*. A small surviving set is not a distinct failure mode; it resolves through the exact same four outcomes as a large one, correctly, with no special-casing required.

**Missing ABV.** Structurally cannot occur as an engine-level input, per Part 5. Flagged there as depending on Product Decisions Register D1's resolution *and* a Catalog Contract 1.0 schema amendment before it could ever become an engine-level concern — not resolved here.

**Unknown style.** Structurally cannot occur as an engine-level input, for the identical reason (`Beer.styleId` non-nullable, per Catalog Contract 1.0). A Beer without a confident Style assignment simply isn't published, per the Catalog Enrichment Playbook's own already-established operational discipline (Part 6 of that document: mark it Unknown, it waits for the next cycle). The engine has nothing to handle here today, and nothing is proposed for it here.

## Part 9 — Testing Architecture

**Pure-function tests.** `generateRecommendation` is already a pure function with zero I/O and zero hidden state — every one of Part 3's nine steps is directly, individually testable by constructing a small in-memory `Catalog` and asserting the returned `RecommendationOutcome`'s exact type and field values. This is the cheapest, most direct testing layer available anywhere in this codebase, and should be the majority of this engine's real test coverage.

**Golden recommendations.** A small, fixed, hand-built `Catalog` fixture (a handful of Beers/Skus/Styles spanning a deliberately varied price/style/value-score range) run through `generateRecommendation` at several fixed budget/style combinations, with each expected `RecommendationOutcome` checked in explicitly — the same "fixture in, checked artifact out" discipline this session already recommended for the Catalog Builder's own golden tests (Catalog Builder Implementation Design, Part 9), applied here to the engine instead of the catalog build.

**Regression tests.** Once a real, Catalog-Builder-produced `catalog.json` exists (rather than today's one-SKU placeholder), a regression suite should assert that a fixed set of realistic budget/style queries against successive real catalog snapshots don't silently flip outcome type (a `RecommendationFound` becoming a `RecommendationTie`, say) without a traceable reason — catching the case where an upstream catalog change (a corrected ABV, a newly-enriched competitor SKU) changes a real recommendation's shape in a way worth a human noticing, not silently absorbing.

**Property tests.** **[Recommendation, not confirmed against existing repository practice]** — no evidence of property-based testing tooling exists anywhere in this Flutter codebase today (not confirmed present or absent by direct inspection for this document; flagged as an open question rather than assumed either way). If adopted, the natural invariants to check, generatively, over randomly constructed catalogs and budgets: every SKU in a `RecommendationFound`/`RecommendationTie` result has `price <= budget`; every SKU in a style-narrowed result resolves to the stated `styleId`; a `RecommendationTie`'s candidates all share the exact same `valueScore`; and no two runs against the identical input ever produce different results (determinism, restated as a property rather than an example).

**Failure fixtures.** A catalog with no SKU at all within a given budget (exercises `NoRecommendationWithinBudget`); a catalog with SKUs within budget but none matching a given style (exercises `NoRecommendationMatchingStyle`); a catalog where the stated `styleId` doesn't exist in `catalog.styles` at all — **worth flagging directly: the real code's own behavior here is to `throw StateError`** (`resolveStyle(catalog, styleId) ?? (throw StateError(...))`), not to return a Recovery-shaped outcome. This is a real, existing design choice — an invalid `styleId` is treated as a programming error (the caller passed something that was never a legitimate style option), not a user-facing Recovery State — and this document does not propose changing it, only naming it as a fixture worth a dedicated test asserting the throw actually happens, rather than leaving that behavior unverified.

## Part 10 — Migration

**What is reused, unchanged, in full.** Every file under `lib/features/recommendation/domain/` — `generate_recommendation.dart`, `recommendation_outcome.dart`, `recommendation_result.dart`, `tied_candidate.dart` — is already the correct engine for catalog integration, exactly as it exists today. Per §0, nothing about loading a real, larger catalog in place of the current placeholder requires any change to this code. This document specifies these four files as-is; it does not redesign them.

**What is deleted.** `models/recommendation.dart`, `models/recommendation_reason.dart`, `policy/recommendation_policy.dart`, `policy/recommendation_profile.dart`, `policy/recommendation_profile_repository.dart`, `policy/profile_policies.dart`, `scoring/weighted_scorer.dart`, `scoring/similarity_strategy.dart`, `services/recommendation_engine.dart`, `widgets/recommendation_profile_bottom_sheet.dart`, and `providers/recommendation_providers.dart` — the entire Generation-1-lineage engine, confirmed unreachable from the real app (already established in the Recommendation Widget Specification: `recommendation_providers.dart` is never imported by the real `RecommendationScreen`). **This is real, well-engineered code — the strategy pattern, the policy injection, the score-and-explain-together discipline are all genuinely good design** — but it implements a product surface (ranked "Similar beers"/"Better value alternatives" lists, and a "recommendation profile" persona-switcher) that has no canonical basis anywhere in the current architecture, and in the case of the inline recommendation lists on Beer Detail, directly contradicts the Beer Detail Screen Contract's own explicit prohibition against surfacing an unprompted alternative. Deleting it is not a loss of working functionality the product actually has — it's removing dead code for a feature that was never canonically authorized to exist in the first place, already flagged as such in the Beer Detail Experience Specification.

**What is recovered, conceptually, not literally.** Per Part 6: the *pattern* Gen1's `WeightedScorer`/`SimilarityStrategy` pair implements — combining multiple scoring dimensions while guaranteeing each dimension's explanation reuses the exact comparison that produced its score — is the correct shape to reach for **if and when** a second ranking dimension is ever added to Recommendation (strength, size, brand, per the real engine's own already-named extension seam). This is not a recommendation to reuse any of the deleted files themselves — their `RecommendationReason` enum and scoring thresholds are tuned for a "similar beers" product surface this document does not resurrect — only their underlying architectural discipline, to be re-expressed fresh, inside `domain/`, the day a real second dimension is actually specified by a future Product Decision. Nothing here authorizes building that today.

**What remains unchanged.** Everything in Part 1's "does not own" list — input gathering, Planning Mode, session state, presentation, catalog construction, every other reasoning surface's own domain — none of it moves, none of it is touched by anything in this document.
